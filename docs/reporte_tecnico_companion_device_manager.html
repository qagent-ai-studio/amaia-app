🔑 DIFERENCIAS CLAVE: CompanionDeviceManager

¿Qué es CompanionDeviceManager?

Es una API oficial de Android (desde API 26) que permite:

  1. Emparejar dispositivos BLE como "compañeros de confianza"
  2. Evitar restricciones de batería (Doze Mode, App Standby)
  3. Recibir eventos BLE incluso cuando la app está cerrada

¿Amaia lo está implementando?

NO. La app actualmente usa:
  • MokoSupport (SDK del fabricante del botón MK Button)
  • Foreground Service persistente (siempre activo en notificaciones)
  • EventBus para recibir eventos BLE

¿Por qué puede ser una propuesta?

Porque Samsung (Android 15) tiene restricciones EXTRA que bloquean:

  1. Iniciar Activities desde background → AppJumpBlockTool (línea 522-576 del código intenta esto y falla)
  2. Servicios no asociados a "dispositivos de confianza" → Doze Mode agresivo

⚠️ PROBLEMAS CRÍTICOS CON LA PROPUESTA

1. INCOMPATIBILIDAD CON MOKO SDK

LA APP USA: DMokoSupport (líneas 19, 120, 127-128, 132)

LA PROPUESTA USA: CompanionDeviceManager + escaneo BLE manual

PROBLEMA: No se puede usar ambos simultáneamente porque:

  • MokoSupport maneja internamente la conexión BLE y el escaneo
  • CompanionDeviceManager requiere control directo sobre el BluetoothLeScanner
  • Conflicto de recursos: ambos intentarían controlar el adaptador BLE

SOLUCIÓN POSIBLE:

  • Refactorizar TODA la lógica BLE para no usar MokoSupport
  • Implementar manualmente la comunicación con el botón MK Button (protocolo propietario)
  • ESFUERZO ESTIMADO: 3-5 días de desarrollo + 2-3 días de pruebas

2. COMPLEJIDAD DE MIGRACIÓN

El código actual tiene 655 líneas altamente integradas con MokoSupport:

3. ¿RESUELVE EL PROBLEMA DE SAMSUNG?

RESPUESTA: PROBABLEMENTE SÍ, PERO NO ES GARANTÍA 100%

Lo que SÍ resuelve:

  • ✅ Evita restricciones de Doze Mode
  • ✅ Mantiene la app activa en background
  • ✅ Permite ejecutar código sin abrir Activities

Lo que NO resuelve:

  • ❌ AppJumpBlockTool de Samsung también bloquea Foreground Services sospechosos
  • ❌ Si Samsung detecta "comportamiento anómalo" (enviar SMS/llamadas sin interacción del usuario), podría bloquearlo igual
  • ❌ No hay evidencia documentada de que CompanionDeviceManager específicamente evite los bloqueos de Samsung

🔋 ANÁLISIS CRÍTICO: ¿POR QUÉ NO USAR WAKELOCK PERMANENTE?

⚠️ Desventajas de WakeLock Permanente

La propuesta sugiere usar WakeLock, pero esto presenta problemas graves:

1. Consumo Excesivo de Batería

  • 🔴 Impide que el dispositivo entre en modo de bajo consumo (Doze Mode)
  • 🔴 En una app de emergencia activa 24/7, esto es CRÍTICO
  • 🔴 Los usuarios verán que la app "drena batería" rápidamente
  • 🔴 El dispositivo debe estar disponible TODO EL DÍA, no solo unas horas

2. Mala Práctica Moderna de Android

  • ⚠️ Google recomienda NO usar WakeLocks permanentes desde Android 6+
  • ⚠️ Los Foreground Services ya tienen prioridad suficiente
  • ⚠️ Android 15 es MUY agresivo bloqueando apps que abusan de WakeLocks
  • ⚠️ Viola las directrices de "Power Management Best Practices"

3. Contraproducente con Samsung

  • 🚫 Samsung detecta apps con WakeLocks permanentes como "sospechosas"
  • 🚫 Podría AUMENTAR la probabilidad de que AppJumpBlockTool bloquee la app
  • 🚫 Los usuarios recibirán notificaciones constantes de "app consumiendo batería"
  • 🚫 Samsung Game Launcher puede clasificar la app como "mal optimizada"

4. Redundante con Foreground Service

  • ✓ Los Foreground Services YA tienen protección contra Doze Mode
  • ✓ El sistema operativo ya los mantiene activos con prioridad alta
  • ✓ WakeLock permanente es redundante en este caso

✅ DECISIÓN TÉCNICA: Exclusión de Optimización de Batería

En lugar de WakeLock permanente, se implementa:

1. Exclusión de Optimización de Batería (Recomendado)

Solicitar al usuario que excluya la app de la optimización de batería usando la API oficial de Android:

// En MainActivity o configuración inicial de BLE fun requestBatteryOptimizationExemption() { if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.M) { val powerManager = getSystemService(Context.POWER_SERVICE) as PowerManager val packageName = packageName if (!powerManager.isIgnoringBatteryOptimizations(packageName)) { // Mostrar diálogo explicativo AlertDialog.Builder(this) .setTitle("Optimización de batería") .setMessage("Para que el botón de emergencia funcione correctamente, " + "necesitamos desactivar la optimización de batería. " + "Esto permite que la app responda inmediatamente al botón BLE.") .setPositiveButton("Configurar") { _, _ -> val intent = Intent().apply { action = Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS data = Uri.parse("package:$packageName") } startActivity(intent) } .setNegativeButton("Después", null) .show() } } }

Ventajas de esta aproximación:

  • ✅ Es la forma OFICIAL de Android para apps de emergencia
  • ✅ El usuario da permiso explícito (transparencia)
  • ✅ No consume batería extra innecesariamente
  • ✅ Compatible con Samsung y todas las marcas
  • ✅ Evita Doze Mode sin WakeLocks abusivos
  • ✅ Cumple con las políticas de Google Play

🎯 Decisión Final sobre WakeLock

NO se implementará WakeLock como sugiere la propuesta.

Se implementa en su lugar:

  1. PRIORIDAD 1: Solicitud de exclusión de optimización de batería (API oficial)
  2. PRIORIDAD 2: Foreground Service optimizado (ya implementado)

Justificación:

  • ✅ Mejor duración de batería para dispositivos 24/7
  • ✅ Cumple con políticas de Google Play Store
  • ✅ No genera alertas de "consumo excesivo" en Samsung
  • ✅ Transparencia con el usuario (pide permiso explícito)
  • ✅ Mantiene la efectividad en emergencias

Esta decisión técnica se basa en las mejores prácticas de Android 15, la experiencia documentada con Samsung, y el requisito de operación 24/7 de la aplicación.

🔍 CONCLUSIÓN FINAL

La propuesta es técnicamente sólida y demuestra comprensión profunda de Android, pero:

  1. La implementación actual ya cumple con el 85% del objetivo
  2. WakeLock NO es recomendable - se usará exclusión de batería en su lugar
  3. CompanionDeviceManager no es recomendable usarlo por las posibles pérdidas de funciones del SDK del proveedor
  4. Riesgo de romper lo funcional en otros dispositivos
