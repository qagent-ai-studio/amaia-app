Hallazgo 1 · Configuración contradictoria

android/gradle.properties ya declara flutter.compileSdkVersion=36 y flutter.targetSdkVersion=36, pero android/app/build.gradle:23,44 los pisa con 35 hardcodeado (commit 3e4f7a2). Al subir la toolchain hay que quitar el hardcodeo o actualizarlo, no dejar las dos fuentes de verdad peleando.

Hallazgo 2 · Bloqueador que Play todavía no reportó

Las librerías nativas del APK release están alineadas a 4 KB, no a 16 KB. Play exige soporte de páginas de 16 KB para apps que apuntan a Android 15+, así que esto habría bloqueado la publicación de todos modos.

lib/arm64-v8a/libapp.so        4K: True   16K: False
lib/arm64-v8a/libflutter.so    4K: True   16K: True
lib/armeabi-v7a/libapp.so      4K: True   16K: True
lib/armeabi-v7a/libflutter.so  4K: True   16K: False
lib/x86_64/libapp.so           4K: True   16K: False
lib/x86_64/libflutter.so       4K: True   16K: False

Los ELF sí traen LOAD align 0x10000 (64 KB, correcto): el problema no es el motor de Flutter sino el zipalign de 4 KB que hace AGP 8.1. Se corrige solo al pasar a AGP ≥ 8.5.1, pero hay que verificarlo explícitamente antes de publicar.

El orden importa. Compilar después de cada paso, no al final: si algo se rompe hay que saber cuál de los cuatro cambios fue.

Upgrade de Flutter

El tramo más incierto. Saltar de 3.24.4 a 3.35.x arrastra Dart 3.5 → 3.9 y un upgrade mayor de casi todas las dependencias.

3–5 días

targetSdk 36 y cambios de comportamiento

Recién aquí se sube el número. Cada punto de abajo es trabajo real que Android 16 impone a apps que apuntan a API 36, no solo verificación.

Verificación

La app es un sistema de alerta para adultos mayores: la regresión que importa no es la UI, es que el botón llegue a producir una llamada.

05
1 día

Publicación

Dado el volumen de cambio acumulado, no saltarse etapas de testing aunque la fecha apriete.

Dónde está concentrado el riesgo

  • ~35%El fork de workmanager (fase 2). Es una dependencia git sin mantenimiento desde la era Flutter 3.13, y sostiene las tareas en background de iOS. Si no se rescata, el alcance de la fase 2 cambia por completo.
  • ~25%Los intents del flujo de emergencia (fase 3c). Es el único punto donde un cambio de Android 16 puede romper silenciosamente la función que da sentido a la app.
  • ~40%Repartido entre Kotlin 2.x sobre los módulos de MokoSmart, el upgrade mayor de dependencias y el trabajo de edge-to-edge.

Por eso el spike sobre workmanager está en la fase 0 y no en la 2: es la incógnita más cara y la más barata de despejar por adelantado.
